# Gather Web — Architecture & Migration Plan

_Started 2026-09-12. Replaces the Salesforce-era `gather_apex_architecture.md`/`gather_frontend_architecture.md` as the going-forward reference for this project. The Salesforce SFDX project (`eventio` repo) remains untouched as the design spec this build was ported from — see its `project/` docs for the original ERD, business rules, and LWC screen inventory this plan translates._

_Companion docs: `gather_web_user_journeys.md` (narrative Planner/Vendor flows told against the routes and RLS policies below), `gather_web_epic_roadmap.md` (the living, phase-by-phase execution plan — kickoff sequence, outstanding items, progress log index), and `gather_web_admin_architecture.md` (the internal-staff-facing admin/support console — a separate route namespace and authorization model layered on top of this same data, planned as Phase 10). This doc stays the stable reference: stack, data model, authorization, routes, and the dated engineering log of what's actually been built and verified._

## Context

Gather's backend was fully built on Salesforce (158 Apex classes, 253 passing tests, a working ERD) and the LWC frontend was partially planned/built on top of it. Investigating a licensing question (self-registering vendors need Account-create permission, which requires a Customer Community **Plus** license) surfaced a deeper structural problem: Salesforce Experience Cloud licenses are priced per external login/member — every additional free signup is a recurring cost that scales with the project's best-case outcome (growth). That's the wrong cost shape for a project explicitly optimizing for free signups and viral growth.

Decision made with the project owner: **fully migrate off Salesforce** to a modern, usage-priced web stack. The existing Salesforce data model and business rules (ERD, Apex architecture, the LWC screen/navigation inventory) were treated as a **design spec to port**, not code to reuse — this plan translates that spec into a new system, not a copy of the old one.

## Repository layout (monorepo since 2026-09-25, epic L1)

The repo is an npm-workspaces monorepo with Turborepo. Every path in these docs is relative to the repo root.

```
gather/                     (repo root — run every command from here)
├─ apps/
│  └─ web/                  @gather/web    the Next.js website (Vercel)   — src/, public/, next.config.ts, .env.local
│  └─ mobile/               (added in epic L6: the Expo iOS + Android app)
├─ packages/
│  ├─ db/                   @gather/db     Drizzle schema (all tables, RLS, grants) + generated SQL migrations
│  ├─ shared/               @gather/shared framework-free TypeScript used by web AND native: business rules,
│  │                                       formatting, vendor ranking, email rendering, FAQ / static content
│  └─ tokens/               @gather/tokens the three colour themes as data (oklch + hex), radii, fonts
├─ supabase/                local Supabase config + the hand-written SQL migrations (storage buckets, helper functions)
├─ e2e/                     Playwright end-to-end + security suites (npm run e2e)
├─ docs/                    the authoritative project docs
└─ turbo.json               Turborepo task pipeline (typecheck, lint, test, build)
```

**Why**: the native apps (epic L6+) share the database, the business rules and the branding with the website; one repo means one change updates all of them and nothing is copied. See `docs/gather_launch_roadmap.md`.

**Rules of thumb**
- `@gather/shared` must stay framework-free (no Next, no Supabase client, no `node:` modules) so React Native can import it. Anything that reads the database, uses the service role, or needs `node:crypto` stays in `apps/web`. Modules that mixed the two were split (`upcoming`, `vendor-ranking`): the pure half is in the package, the web file re-exports it and keeps only the fetching.
- Workspace packages are consumed as TypeScript source (`exports` point at `src/*.ts`); Next compiles them via `transpilePackages` in `apps/web/next.config.ts`.
- Change a theme colour in **both** `apps/web/src/app/globals.css` and `packages/tokens/src/themes.ts`; a test fails if they differ (and Turborepo is told the CSS is an input of that test, so a cached pass can't hide the drift).
- Old `supabase/migrations/*.sql` files still say `src/db/schema.ts` in comments. They are applied migrations and must never be edited, so those comments are now stale by design.

## Product Design Principles (carried forward)

Ported from `gather_erd_master.md`'s Design Principles — these shape *scope*, not just data model, so they belong up front rather than buried in a table:

- **Individual consumers are the primary target user** (weddings, birthdays, anniversaries). Professional/multi-client planners are a deliberately deferred, not-blocked use case — modeled later as an `event_collaborators` row with elevated `permission_level` on someone else's event, no new table required. **Implication:** don't build multi-client planner dashboards or portfolio views until this is explicitly prioritized.
- **Early on, most planners are self-managing their own event with little or no vendor-side participation** — the vendor directory starts empty/community-sourced (see Vendor Directory Bootstrapping below), and most vendors a planner deals with won't be actively using Gather themselves for a while. **Implication:** planner-facing tracking features (payment plans, tasks, attendees) must work fully standalone, without requiring the vendor on the other end to ever open the app — this is exactly why payment plans are planner-owned end to end (see the quotes-vs-payment-plans ownership rule in Business Rules & Invariants) rather than something negotiated with a vendor account.
- **Free directory model for now** — no commission/platform-fee fields anywhere in the schema. Monetization mechanics are undecided and out of scope. **Implication:** resist adding payout/commission columns to `vendors`/`event_vendors` speculatively.
- **Manual payment tracking today, gateway integration planned.** `payment_installments` already reserves `payment_gateway`/`gateway_transaction_id`/`gateway_status` columns for Stripe (Phase 7), but nothing calls a gateway yet — every installment is marked paid by hand. **Implication:** don't wire Stripe early; the schema is already shaped so that phase is additive, not a migration.
- **South Africa-only for launch: single currency (ZAR), fixed timezone (SAST/Africa Johannesburg)** — an explicit placeholder, not permanent architecture. Every amount is a plain ZAR number (no currency-code column), and `events` stores real `timestamptz` values (not a hardcoded offset) specifically so a future multi-timezone picker is additive. **Implication:** hardcode `Intl.NumberFormat('en-ZA', { style: 'currency', currency: 'ZAR' })` for now rather than building currency selection; see Open Questions below for what changes later.
- **Mobile-first** — planning happens primarily from a phone. Already enforced procedurally, not just as a principle: see this doc's Verification section for the real-device testing requirement (`npm run dev:mobile`, phone testing over every Vercel preview) before any phase is considered done.

## Recommended Stack (reasoned out)

| Layer | Choice | Why |
|---|---|---|
| Frontend | **Next.js (App Router, React)** | Largest ecosystem, easiest to hire for later, first-class support on every host below. Server Components + Server Actions replace a lot of what Apex controllers did. |
| Database | **Postgres via Supabase** | Supabase = hosted Postgres + Auth + Storage + **Row Level Security** in one free-tier product. RLS is a near-exact conceptual replacement for Salesforce's OWD-Private-plus-explicit-sharing model the ERD already relies on — same mental model, different syntax. Not a lock-in: it's plain Postgres, portable to any Postgres host if you ever outgrow Supabase. |
| Auth | **Supabase Auth** | Bundled, free up to a generous MAU threshold, integrates directly with RLS via `auth.uid()`. Handles email/password + social login, replacing `Site.createExternalUser`/`SalesforceSiteRegistrar` entirely — and removes the whole license-tier problem that started this investigation, because there's no per-login fee at all. |
| ORM | **Drizzle** | Thin, SQL-close, fully typed — a good match for a developer used to writing precise Apex/SOQL rather than fighting a heavy abstraction. |
| Background jobs | **Supabase Edge Functions + `pg_cron`**, or **Inngest** if durable retries/step functions are needed | Replaces the hourly reminder Queueable. Inngest's free tier gives Salesforce-Queueable-like per-step retry semantics if the reminder/payment logic gets complex. |
| Payments | **Stripe** | The original ERD already reserved `Payment_Gateway__c`/`Gateway_Transaction_Id__c`/`Gateway_Status__c` fields for this — carries a design decision already made, not a new one. |
| File storage | **Supabase Storage** | Cover images, quote documents — same product as the DB/auth, one less vendor to integrate. |
| Hosting | **Vercel** (app) + **Supabase** (data/auth/storage) | Both have real free tiers today and both bill on usage (bandwidth/compute/rows), not per registered user — the actual property being optimized for. Flag: Vercel bandwidth pricing is the one line item worth watching if traffic gets very large; Supabase/Postgres compute is cheap and predictable by comparison. |

This is "boring technology" on purpose — every piece here is mainstream, well-documented, and replaceable independently, so a big traffic spike is a scaling problem to solve with money, not a rewrite.

## Data Model Port (Salesforce ERD → Postgres)

| Salesforce entity | Postgres table | Notes |
|---|---|---|
| Person Account / User | `users` (managed by Supabase Auth) + `profiles` | Profile row keyed to `auth.users.id`. |
| Event__c | `events` | `owner_id`, `status`, `visibility`, `event_type`, `start_at`/`end_at` (real `timestamptz`, no hardcoded timezone), `capacity`, `location`, `description`, `cover_image_url`. |
| Event_Collaborator__c | `event_collaborators` | Join table: `event_id`, `user_id`, `permission_level`, `status`. Drives an RLS policy, see below. |
| Event_Attendee__c | `event_attendees` | `event_id`, nullable `contact_user_id`, fallback `name`/`email`/`phone`, `rsvp_status`, `guest_count`. |
| Event_Task__c | `event_tasks` | `event_id`, `title`, `due_date`, `completed`, `priority`, `assigned_to`. |
| Event_Vendor__c | `event_vendors` | `event_id`, `vendor_id`, `status`, `amount`, `confirmed`. |
| Account (Vendor record type) | `vendors` | Discriminator not needed as a separate record type — vendors get their own table instead of sharing `accounts`. `verification_status`, `primary_category`, `created_by`. |
| Vendor_Service__c | `vendor_services` | `vendor_id`, `name`, `description`. |
| Vendor_Claim_Request__c | `vendor_claim_requests` | `vendor_id`, `status`, `notes`, `reviewed_by`, `reviewed_at`, `rejection_reason`. Partial unique index enforces one Approved per vendor. |
| Vendor_Team_Invite__c | `vendor_team_invites` | `vendor_id`, `invited_email`, `role`, `status`. |
| AccountContactRelation | `vendor_team_members` | `vendor_id`, `user_id`, `role` (owner/manager/staff), `is_active`. |
| Vendor_Quote__c | `vendor_quotes` | `event_vendor_id`, `amount`, `status`, `valid_until`, `document_url`. Partial unique index: one Accepted per `event_vendor_id`. |
| Payment_Plan__c | `payment_plans` | `event_vendor_id`, `total_amount`, `deposit_amount`, `deposit_due_date`, `status`. |
| Payment_Installment__c | `payment_installments` | `payment_plan_id`, `installment_number`, `due_date`, `amount`, `status`, `paid_on`, `payment_gateway`, `gateway_transaction_id`. CHECK/trigger keeps sum ≤ plan total. |
| Payment_Reminder__c | `payment_reminders` | `payment_installment_id`, `remind_at`, `method`, `sent`. |

**Invariant enforcement** (was Apex trigger "backstops"): use **partial unique indexes** and **CHECK constraints** at the DB level in addition to app-level checks — e.g. `CREATE UNIQUE INDEX ON vendor_quotes (event_vendor_id) WHERE status = 'Accepted'`. This is strictly better than the Salesforce version: it's synchronous and unconditional, no async recalculation lag to work around.

## Business Rules & Invariants

Consolidated from `gather_erd_master.md` (scattered across Design Principles, object notes, and the Persona Model section) into one reference, each tagged with where it's actually enforced:

| Rule | Enforced where |
|---|---|
| Only one `Accepted` quote per `event_vendor_id` at a time | Partial unique index on `vendor_quotes` (see Data Model Port above) |
| Only one `Approved` claim per vendor | Partial unique index on `vendor_claim_requests` |
| **Approving a claim auto-rejects every other competing `Pending` claim on the same vendor** (multiple planners/vendors can submit competing claims; only one can win) | Server Action (`approveClaim`) — reject the others in the same transaction as the approval, not just relying on the unique index to block a second approval later |
| Installment amounts for a plan can never sum to more than the plan's `total_amount` | CHECK constraint / trigger on `payment_installments` |
| An installment can't be marked paid while its payment plan is still `draft` — a draft plan's total/deposit can still change, and the installment-sum check only validates against whatever `total_amount` happens to be *right now*; "Activate Plan" is what draws a line under the numbers first | Server Action (`markInstallmentPaid`) checks the parent plan's status before writing — not RLS, since this is workflow sequencing for the same planner/editor, not a cross-user access boundary. The UI hides the "Mark Paid" button the same way, but the Server Action re-checks regardless, since a direct POST would bypass a UI-only guard. |
| Vendor role tiers — **Owner** (edit business profile, manage team membership) > **Manager** (submit/manage quotes, manage `vendor_services` listings) > **Staff** (chat, add gallery photos, team notes on bookings, *suggest* quotes for a Manager to send; no prices or payments — revised 2026-09-24, see changelog "Staff permissions") | `assertVendorAccess(vendorId, minRole)` Server Action guard (see Authorization Model Port below), re-checked per call |
| A vendor self-registering a brand-new business becomes its Owner immediately, no review needed (no competing claim possible on a listing that didn't exist yet) | Application logic in the vendor-registration Server Action |
| A claimant becomes Owner the moment their claim is approved | Application logic in `approveClaim`, same transaction as the auto-reject rule above |
| Before creating a new vendor stub, the UI must require searching existing vendors first and confirming no match | UX-level dedupe step in the add-vendor flow — not a DB constraint, matching the Salesforce-era decision that a hard uniqueness constraint on vendor name would produce false positives |
| A professional/multi-client planner is a deferred, not-blocked persona — modeled as an `event_collaborators` row with elevated permission, no new table | Schema already supports it (see Product Design Principles above); the actual elevated-permission UI is unbuilt — tracked in Open Questions below |
| **Removing a vendor from an event (`removeVendorFromEvent`) deletes its payment plan and unlinks it from any budget line** — `event_vendors` itself is only ever soft-removed (`status -> 'rejected'`, preserving chat history), but a removed vendor's `payment_plans` row (and, via cascade, its `payment_installments`) is a real delete, and any `budget_items.event_vendor_id` pointing at it is cleared back to null. Safe specifically because `hasPaidInstallment` already blocks the whole removal while any installment on the plan is still actually paid — nothing left on the plan by the time this runs is worth preserving as an orphaned "removed vendor's plan." | Server Action (`removeVendorFromEvent`) — the plan delete needed a new `payment_plans_delete_event_editor` RLS policy (migration `0027`), since none existed before (deleting a plan was previously impossible at all, by design, until this) |
| **Quotes and payment plans have deliberately opposite ownership** — a quote is created and revised by the vendor (owner/manager) and only accepted/declined by the planner; a payment plan is created and maintained entirely by the planner (owner/editor collaborator) — the vendor can see it (so they know what's been agreed) but never write to it. This isn't a UI convention, it's enforced at the RLS layer: `vendor_quotes_insert_vendor_manager` vs. `payment_plans_insert_event_editor`/`payment_plans_update_event_editor`, which has no vendor-side branch at all (see the schema's own comment on that policy). Worth stating explicitly here because the two features sit right next to each other in the UI and are easy to mentally merge into "the vendor manages the money side" — they don't; a payment plan is closer to a planner's private budget tracker that happens to be scoped to a specific vendor booking, not a shared/negotiated document the vendor edits. |

## Vendor Directory Bootstrapping & Verification

Ported from `gather_erd_master.md`'s "Vendor Directory Bootstrapping & Verification" section — at launch the directory has no seed data and no vendor has self-registered, so it's **community-sourced**:

1. **Creating a stub.** Any authenticated planner can create a `vendors` row with just a name, category, and basic contact info (phone/website) — from `/vendors/add` (see Screen/Route Inventory below), after the dedupe-search step above confirms no match exists. `verification_status` starts at `unclaimed`.
2. **Directory visibility.** Unclaimed vendors appear in the public `/vendors` directory like any other, marked with an **Unverified** badge — this is what makes the crowd-sourced approach useful before real vendors arrive, and gives a vendor a reason to notice and claim their listing.
3. **Claiming.** A vendor finds their (possibly stub) listing at `/vendors/[id]/claim`, submits a `vendor_claim_requests` row with a short verification message. `verification_status` moves to `claim_pending`.
4. **Review.** Unlike Salesforce (an admin list view + Flow inside Setup — no custom screen needed), gather-web has no back-office by default, so this needs an **actual admin screen** — tracked in "What must actually get fixed this time" below as net-new work, not a straight port. Approving provisions the claimant as Owner in `vendor_team_members`, flips `verification_status` to `verified`, and auto-rejects any other competing `Pending` claims (see Business Rules & Invariants above). An admin can also mark a vendor Verified directly, without a claim, for hand-onboarded vendors.
5. **Duplicate vendors** that slip through the UX dedupe step are an admin merge, not a blocking concern — same as the Salesforce-era decision.

## Authorization Model Port (Sharing → RLS)

- **Owner-only until shared** (`events`, `vendors`): default-deny RLS policy, `USING (owner_id = auth.uid())`, then an additional `OR EXISTS (SELECT 1 FROM event_collaborators WHERE event_id = events.id AND user_id = auth.uid())` clause — a direct translation of `EventSharingManager`'s explicit-grant-on-invite-accept pattern.
- **Vendor team visibility** (`event_vendors` visible to the vendor's whole active team): RLS policy joining through `vendor_team_members` — same shape as `EventVendorSharingManager`, but computed live on every query instead of snapshotted at association time. This is a real improvement over the documented Salesforce limitation ("a teammate added after a booking already existed won't see it") — carry over the fix, not the bug.
- **Guest/public access** (published events, vendor directory): a plain RLS policy for `anon` role, `USING (status = 'Published' AND visibility = 'Public')` — no async Guest User Sharing Rule recalculation to reason about at all, a direct simplification.
- **Guest writes** (RSVP): keep the "narrow allow-listed DTO, not raw table access" principle from `GuestRsvpRequest` — implement as a Server Action or API route with an explicit small input shape, using the Supabase service role internally, never a client-side anon INSERT policy on the raw table.
- **Role-tiered vendor permissions** (Owner > Manager > Staff): a small `assertVendorAccess(vendorId, minRole)` helper (direct port of `UserContextService.assertVendorAccess`) called at the top of every vendor-scoped Server Action, re-checked per call — same stateless-per-call philosophy as the Apex version, not cached in a session.

## What becomes moot (Salesforce-specific, does not carry over)

Account-creation license restriction; `Gather_Member_Access` permission-set-assignment gap; Person Account self-edit sharing errors; `RunSpecifiedTests` coverage fragility; LWR CSP font-loading workaround; LMS late-subscriber replay bug; `DigitalExperience`/`ExperienceBundle` metadata retrieval quirks. None of these exist once there's no Salesforce sharing/licensing/permission model underneath.

## What must actually get fixed this time (universal, carries forward as real product work)

Guest home not branching on auth state; RSVP validation robustness; URL not reflecting current tab/view (a router now makes this free, not extra work); bare `R{amount}` string formatting → real `Intl.NumberFormat` currency formatting; vendor-team "snapshot at association time" sharing semantics (fix via live RLS join, above); claim approve/reject needs a minimal back-office UI (was deliberately out of scope before — now scoped as Phase 10, see `gather_web_admin_architecture.md`); notification preferences need an actual schema (never existed); and — called out explicitly because it never happened once across 22 LWC bundles — **this rebuild should have real component/integration tests from the start** (Vitest + React Testing Library), not deferred to "later."

## Open Questions (carried forward)

Ported from `gather_erd_master.md`'s Open Questions — these don't block current work but need answers eventually:

1. **Professional planner permission mechanics.** `event_collaborators` is designed to support this later (see Product Design Principles above), but the exact permission model — can a collaborator manage payments? invite other collaborators? — isn't defined yet.
2. **Multi-currency / multi-timezone**, once the target market broadens beyond South Africa. Both are deliberately deferred as one future migration rather than two, since `events` already stores real `timestamptz` values and adding a currency-code column alongside the existing plain-ZAR amounts is additive either way.
3. **`event_type` as a Postgres enum vs. an admin-configurable table.** Currently a plain `text` column (not even a `pgEnum`) — the loosest possible placeholder — deliberately left unconstrained rather than guessing at a fixed value set upfront; revisit once real usage shows whether a `pgEnum` (fixed set, needs a migration to extend) or an admin-configurable table (editable without a deploy) fits better.

The Salesforce-era Experience Cloud licensing question (Partner vs. Customer Community Plus for self-registering vendors) is **moot** here — see "What becomes moot" above; Supabase Auth has no per-login license tiers, and the equivalent self-registration flow has already been proven end-to-end in the Phase 0 RLS verification (see the engineering log below).

## Verification

Each phase: deploy to a Vercel preview branch against a Supabase branch/dev database, exercise manually in a real browser (not just curl — a real gap in the old build), and add Vitest/RTL tests (`npm test`) for the components and Server Actions built in that phase before moving on. Data-model invariants (one Accepted quote, one Approved claim, installment sum ≤ plan total) get a direct SQL test against the constraints, not just app-level assertions.

**A real limit on what "add tests" can mean here**: per Next.js's own Vitest guide, async Server Components aren't supported by Vitest at all — and every `page.tsx` in this project is one. Vitest/RTL's job is the shared UI primitives (`apps/web/src/components/ui/*`) and pure functions (`packages/shared/src/utils.ts`); pages and Server Action business logic stay covered by the manual real-browser pass each phase already does, which is the correct strategy for that layer, not a stopgap for it.

**Mobile-first real-device testing** (this is a bottom-tab-bar, mobile-first product — desktop devtools emulation is not sufficient on its own): during active development, run `npm run dev:mobile` (binds to `0.0.0.0`) and hit `http://<pc-local-ip>:3000` from a phone on the same Wi-Fi for live-reload testing; when that's blocked (cellular data, network client isolation, or a flow needing real HTTPS such as an auth redirect) use a tunnel (Cloudflare Tunnel / ngrok) for a real `https://` URL to the local server. Once deploying regularly, each Vercel preview URL doubles as the real-device test target and should be opened on an actual phone, not just resized in a desktop browser, before a phase is considered verified — specifically checking iOS Safari's `100vh`/viewport-height quirks and safe-area insets around the fixed bottom tab bar, which devtools emulation does not reliably surface.

## Local environment setup log

- **2026-09-12**: Repo scaffolded at `C:\Dev\Eventio\gather-web` via `create-next-app` (TypeScript, Tailwind, App Router, ESLint). Installed `drizzle-orm`, `drizzle-kit`, `postgres`, `@supabase/supabase-js`, `@supabase/ssr`, and the `supabase` CLI as project dependencies. Vercel CLI installed globally. Chose the **full local Docker + Supabase CLI stack** for local Postgres/Auth (over a cloud-only dev project) — this requires Docker Desktop, which in turn requires WSL2, both needing Administrator privileges to install. Docker Desktop additionally needs CPU virtualization enabled in the BIOS/UEFI firmware (a separate setting from WSL2 itself — Windows reports it via `systeminfo`'s "Virtualization Enabled In Firmware" line). See root `README.md` for the one-time setup commands.

- **2026-09-12 (later same day): full Phase 0 schema + RLS baseline built and verified against the real local stack**, not just type-checked. What shipped:
  - All 15 tables from the Data Model Port table above, in `packages/db/src/schema.ts`, using Drizzle's `pgEnum`/`pgTable`/`index`/`pgPolicy` and the `drizzle-orm/supabase` helpers (`authUid`, `authenticatedRole`, `anonRole`). Every table has `.enableRLS()` — deny-by-default, matching Salesforce's Private OWD posture — with real policies on `events`, `event_collaborators`, `vendors`, `vendor_team_members`, and `event_vendors` (the Phase 0 "baseline" scope); every other table is locked to service-role-only until its owning feature phase adds policies.
  - Indexes on every foreign-key column an RLS policy actually filters/joins on (`events.owner_id`, both `event_collaborators` FKs, `vendors.created_by`, both `vendor_team_members` FKs, both `event_vendors` FKs) — Postgres doesn't auto-index FK columns, and RLS policies run `EXISTS` subqueries on exactly these columns on every request.
  - A Postgres trigger (`supabase/migrations/00000000000001_profiles_on_signup.sql`) that creates a `public.profiles` row automatically whenever `auth.users` gets a new row via Supabase Auth signup, plus a `profiles.id → auth.users.id ON DELETE CASCADE` foreign key Drizzle can't express (it doesn't manage the `auth` schema).
  - Four `SECURITY DEFINER` SQL helper functions (`supabase/migrations/00000000000002_rls_helper_functions.sql`: `is_event_owner`, `is_event_collaborator`, `is_vendor_creator`, `is_vendor_team_member`) that every cross-table policy now calls instead of inlining `EXISTS` subqueries against another RLS-protected table.

  **Three real bugs found and fixed by testing through the actual enforcement path, not just structurally inspecting the schema — this is the reason none of this was declared "done" after the first `drizzle-kit push` succeeded without error:**
  1. **`drizzle-kit push` silently drops RLS policy conditions.** After pushing the full schema, `pg_policies.qual`/`with_check` were `NULL` for every single policy — `push` diffs live against the DB via introspection rather than executing the generated SQL file verbatim, and has a real bug serializing policy expressions through that path (confirmed by comparing against `drizzle-kit generate`'s output, which had the correct SQL all along). **Fix: never use `db:push` once RLS policies exist — use `db:generate` then `db:migrate` instead**, which applies the migration file's SQL directly. `db:push` is now a hard-failing script in `package.json` with a pointer back here, specifically so this can't be silently reintroduced later. The very first migration had to be applied by hand (`node -e` running the raw SQL, since `drizzle-kit migrate` didn't yet have a tracking-table row for it) and then retroactively marked as applied in `drizzle.__drizzle_migrations` (hash = sha256 of the migration file's exact bytes, `created_at` = the journal's `when` value) so `db:migrate` would treat it as a baseline going forward.
  2. **"infinite recursion detected in policy" (Postgres error 42P17).** `events`' SELECT policy queried `event_collaborators` to check for an accepted invite; `event_collaborators`' own SELECT policy queried `events` back to check for ownership — two tables whose RLS policies reference each other form a cycle, since evaluating either table's policy requires re-evaluating the other's. The same cycle existed independently between `vendors` and `vendor_team_members`. **Fix: route every cross-table (and self-referencing) RLS check through a `SECURITY DEFINER` SQL function** (the four functions listed above) — such a function's internal query runs as the function's owner, which bypasses RLS, breaking the cycle. This is a general Postgres/Supabase RLS rule, not something specific to a mistake in this schema: any time two tables' policies reference each other, or a table's policy references itself, this same fix applies.
  3. **`DROP SCHEMA public CASCADE` (used once, mid-debugging, to get a clean slate) wipes Supabase's own baseline grants on that schema**, not just the tables in it — `anon`/`authenticated`/`service_role` lost table-level SELECT/INSERT/UPDATE/DELETE entirely, producing a confusing "permission denied for table events" *after* the RLS fixes above were already correct (RLS only ever restricts further; it can't grant access a role doesn't already have at the privilege level). Restored via the standard Supabase grants, saved in `supabase/migrations/00000000000003_restore_public_grants.sql` for the record. **Lesson: never `DROP SCHEMA public` on a Supabase-managed Postgres instance — use `supabase db reset` for a genuine clean slate**, which reruns Supabase's own initialization (grants included) plus everything under `supabase/migrations`.

  1. **A cookie-mutating Server Action discards its own `useActionState` return value before the client can react to it.** The original login form tried to detect a `{ success: true }` return value client-side (to show a toast, then redirect) via a `useEffect`. Cause: Next.js automatically re-renders "the current page" in the same response whenever a Server Action mutates a cookie (ours sets the Supabase auth cookie), and that re-render is closer to a fresh remount than a state update — it discards the in-flight action state before any client-side effect watching it can run. **Fix: redirect server-side, inside the action, on the success path** (`redirect("/")` from `next/navigation`) instead of returning a value for the client to act on; the error path never mutates a cookie, so `useActionState` works normally there. - **2026-09-14 (Full project code review) — a multi-angle review of everything built to date, run against real code, not just a design pass. Found one real, shipped security vulnerability and five real correctness/accessibility bugs, all fixed and re-verified; a further set of duplication/efficiency findings were logged as follow-up rather than fixed immediately, to keep this pass proportionate.**

  **Security — the most serious finding**: `is_admin(p_user_id uuid)` (Phase 10) accepted an arbitrary target id and was granted to `anon`. Since `profiles_select_all_authenticated` already lets anyone enumerate every profile id, a client could loop `rpc('is_admin', { p_user_id: id })` over every id and reconstruct the exact admin roster the function existed to hide — independently found and confirmed by three separate review passes. The fix had two parts, because there were two separate holes: (1) `is_admin()` now takes no argument and checks `auth.uid()` internally (`supabase/migrations/00000000000008`) — it's now structurally impossible to ask about anyone but yourself; (2) direct column access to `is_admin` was revoked outright (`00000000000009`), because Postgres RLS is row-level only — the SECURITY DEFINER function was never sufficient by itself, since the raw column was always readable via PostgREST directly, bypassing the app and the RPC entirely. **A genuine Postgres subtlety hit fixing part 2**: a first attempt (`revoke select (is_admin) ... from anon, authenticated`) executed with no error but had *zero* effect — verified directly against `information_schema.column_privileges`. The reason: a column-level `REVOKE` cannot carve an exception out of the broader table-level `grant all` this project's tables already had (`00000000000003_restore_public_grants.sql`) — the table-level grant simply wins. The actual fix is the reverse order: revoke the table-level `SELECT` entirely, then `GRANT SELECT` back on only the specific columns (`id, display_name, phone, created_at`) that should stay readable. Re-verified against a real `SET ROLE anon` session afterward, both that `is_admin` is now blocked and that legitimate columns still aren't.

  1. **`acceptQuote` accepting a quote left a stale, still-functional "Decline" button on screen that could silently revert the acceptance** — the action's own `revalidatePath` was deliberately dropped earlier to avoid clobbering `useActionState`'s return value, but nothing replaced it, so the page's server-rendered `quote.status === "sent"` check (gating both Accept and Decline) never updated. Fixed with a client-triggered `router.refresh()` in `AcceptQuoteForm` after a confirmed success — this runs *after* `useActionState` already committed the result, so it doesn't hit the original clobbering bug — plus a `.eq("status", "sent")` guard added to both `acceptQuote`'s and `declineQuote`'s own updates as the real underlying invariant, not just a UI-timing fix.   2. **`approveClaim` (the vendor-claim queue) discarded the `{error}` result of 3 of its 4 writes**, so a failed `vendor_team_members` insert would still log `vendor_claim.approved` as a clean success while the documented invariant ("a claimant becomes Owner the moment their claim is approved") silently didn't happen. - **2026-09-14 (iOS Safari kept zooming in on navigation, eventually opening a horizontal scrollbar) — reported from a real iPhone, not reproducible in desktop Chrome, which is itself a clue.** The symptom ("keeps zooming in when I navigate around, then it creates a horizontal scrollbar") is the textbook description of a well-known, specific iOS Safari behavior, not a layout bug: Safari auto-zooms the whole page the instant a focused text input's *computed* font size is under 16px, to keep the text legible. Checked the actual rendered viewport meta tag first, to rule out the more common cause of this class of bug — `curl`'d the homepage and confirmed `width=device-width, initial-scale=1, viewport-fit=cover` was already correctly present (Next.js's `Viewport` export does merge a partial object like this project's `{ viewportFit: "cover" }` with its own framework defaults, contrary to how a partial `metadata` object behaves — worth knowing, since the more common version of this bug really is a missing/broken viewport tag). With that ruled out, checked every text-entry element's actual computed font size instead: the shared `Input` component and every raw `<select>` in the app (event form, notification preferences, RSVP editor, invite forms, and others) were all set to Tailwind's `text-sm`, which is 14px — under the threshold. On a client-routed Next.js app, that auto-zoom doesn't reset between page navigations the way it would after a real full-page reload, so it can compound across a session: zoom in on the first focused input, navigate, the zoom level carries over, and the fixed-width mobile shell (`max-w-sm`, sized for a 1× viewport) eventually renders wider than the effectively-smaller zoomed-in viewport, which is what actually produces the horizontal scrollbar.

  - **A defensive second layer**, since the underlying report was specifically about a horizontal scrollbar appearing: `overflow-x: hidden` on `html`/`body`, added to the existing `@layer base` block. This isn't the fix for the zoom itself — it's a safety net so that if anything, on any device, for any reason, ever renders wider than the viewport again, it clips instead of opening a scrollbar the mobile shell was never designed to have.
