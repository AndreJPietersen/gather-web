# Gather Web — User Journeys

**Status:** Reconciled against shipped reality on 2026-09-16. Originally written forward-looking against Phases 0–1 only, then left unmaintained through Phase 10 and roughly a dozen further feature sessions — this pass rewrote every beat below against what's actually built today (route names, action names, and policy behavior all re-checked against the real code, not carried over from the original draft's guesses). Two citations in the original draft turned out to name things that were never actually built that way (`assertVendorAccess(vendorId, minRole)` doesn't exist — the real helper is `getVendorAccess(vendorId, userId)`; the vendor claim admin review screen was called "net-new, not yet built" when it's been live at `/admin/vendors/claims` since Phase 10) — both fixed below. Going forward, this doc drifting out of date again is a real risk worth watching for, not a one-time mistake already corrected: update a beat inline when the flow it describes changes, the same instruction the original draft gave itself and didn't follow.

_Companion docs: `gather_web_architecture.md` (the data model, RLS policies, route inventory, and the full dated changelog every beat below is grounded in), `gather_web_admin_architecture.md` (the admin/support console, referenced below where a beat crosses into it), and `gather_web_epic_roadmap.md` (phase-by-phase build history and current Progress Log)._

## Part One: The Planner's Journey

She lands on `/` with nothing decided yet — not even an account. The home page shows her real public events and a teaser of verified vendors, because a guest can browse Gather before logging in, plus a small link to the FAQ for anyone still deciding whether to sign up. *(Route: `/`, branching on auth state — a guest-safe query filtered to `status = 'published' AND visibility = 'public'`, the `anon`-role RLS policy on `events`. FAQ link: `src/components/landing/guest-landing.tsx`.)*

She taps **Plan an Event**, enters an email and password, and submits. *(Route: `/register` → Supabase Auth signup — no license tier, no per-login cost, unlike the Salesforce-era `Site.createExternalUser` path it replaces.)* She lands in the app shell and fills in her name and phone to finish onboarding. *(Route: `/onboarding/planner`, a Server Action writing to her own `profiles` row — the `profiles.id → auth.users.id` trigger already created that row automatically on signup.)*

She creates her event — type (a real admin-managed dropdown with an "Other" + free-text fallback, not the plain free-text field it started as), date, location, guest cap — and it starts life as a private Draft only she can see. *(Route: `/events/new`, a Server Action inserting into `events` with `owner_id = auth.uid()`; the owner-only RLS policy is what actually keeps it private, not application logic.)* Her fiancé needs to help plan, so she invites him as an Editor collaborator; he finds the invite waiting for him on his own Profile tab and accepts it. *(An `event_collaborators` row with `permission_level = 'editor'`, `status` moving `invited → accepted` — the RLS policy on `events` includes an `OR EXISTS (... event_collaborators ...)` clause specifically so an accepted collaborator can see an otherwise-private event.)* Once she sets a real date and publishes, her event's own page grows a live countdown — a gradient hero card ticking down to the day, shown to her, her collaborators, and (once public) any guest who opens the link. *(`CountdownCard`, `src/app/events/[id]/countdown-card.tsx` — hidden entirely once the event's start time has passed, both on the server's first render and again client-side if a tab is left open across that moment.)*

She builds a task list and an attendee list, and a guest who was never asked to create an account can still RSVP from a shared link. *(Routes: `/events/[id]/tasks`, `/events/[id]/attendees`; guest RSVP is a Server Action with a narrow, explicit input shape using the Supabase service role internally — never a client-side `anon` INSERT policy on the raw table.)* She sets a total budget and a warning threshold, and adds budget line items as real costs come in — the page tells her plainly whether each line is under or over what she budgeted, comparing against the vendor's full agreed cost, not just what's been paid so far. *(Route: `/events/[id]/budget`; `budget_items`, `events.budget_total`/`budget_warning_percent`.)*

If she's not sure where to start — every one of these is its own independently-reachable page, with no suggested order — a "Help me plan" card sits at the top of her event's page, always there whether the event is brand new or mostly set up. Tapping it opens a five-step guided wizard (attendee, task, budget line, vendor, payment plan) that resumes at whichever step is still genuinely incomplete rather than always restarting at the top, with Skip available on every step since this is guidance, not a gate. *(`HelpMePlanCard`/`HelpMePlanWizard`, `src/app/events/[id]/help-me-plan/` — editor-only; each step either reuses a real existing Server Action unchanged or a deliberate non-redirecting duplicate of one, purely so the modal survives a successful submit instead of being torn down by that action's own page-level `redirect()`.)*

Planning isn't only logistics — she also has a Mood Board, one page where she picks a small color palette, pins a couple of photos as the board's featured pair, scatters the rest in a loose grid, and writes a short tagline capturing the whole vibe. Deliberately separate from the plain photo grid at Gallery, not a replacement for it — this one's meant to feel personal and expressive rather than exhaustive, capped at 12 photos instead of Gallery's 20. *(Route: `/events/[id]/mood-board`; `event_mood_boards`, `event_mood_board_photos`, the private `event-mood-board` Storage bucket — same owner-or-collaborator viewing, owner-or-editor editing as everything else on this event. A live preview of it — real featured photos, real palette dots — sits on the event page itself, just below Help Me Plan.)*

She browses `/vendors` — a real marketplace now, not a plain list: a Featured row up top, then a photo-forward grid of everyone else, ranked by a mix of admin-curated placement and how complete each vendor's own profile is — for a photographer and finds one that isn't listed yet. Rather than give up, she searches first (the required dedupe step) and, finding no match, creates a lightweight stub — name, category, phone. It shows up marked **Unverified**. *(Route: `/vendors/add` — see Vendor Directory Bootstrapping & Verification in the architecture doc.)* For vendors she does find, she associates each one with her event, and the page now surfaces a few Suggested Vendors of its own — ones whose services already match her event's type. *(An `event_vendors` row; the vendor's whole active team sees it immediately via the live RLS join through `vendor_team_members`.)*

Quotes start arriving from vendors who've claimed their listings. She reviews them and accepts the caterer's — any other quote on that relationship gets auto-declined in the same transaction, backstopped by a partial unique index so even a direct database edit can't sneak a second Accepted quote past it. *(Route: `/events/[id]/vendors`.)* With the caterer confirmed (a real toggle on the vendor's own detail page, not just implied by an accepted quote), she sets up a payment plan and installments; the platform won't let the installments exceed the plan total, whether through the normal flow or not. She marks the deposit paid the moment it clears, attaches a photo of the bank confirmation directly to that installment so it's never lost in an inbox, and if a payment ever needs reversing she marks it Refunded rather than the record just vanishing. *(Route: `/events/[id]/payments`; installment-sum CHECK constraint; `proof_of_payment_path` + the private `payment-proofs` Storage bucket; `refunded` installment status.)* As each payment comes due, a reminder actually goes out now — not via a scheduled job (the Edge-Functions-+-`pg_cron`-vs-Inngest decision was deliberately skipped rather than made), but *implicitly*: opening the app fires a one-time check for anything she owns or edits that's due soon or overdue, and email hasn't already gone out for; it lands in her inbox, gets recorded so it never repeats, and shows up as a small "Overdue" flag wherever that payment is already visible (Home's Upcoming Payments, the event card on My Events, a dot on the event page's own Payments tile). *(`checkAndSendPaymentReminders`, `src/components/reminders/actions.ts`; `sendEmail`, `src/lib/email.ts` — Resend in production, the local Supabase stack's own Mailpit catcher in dev when no `RESEND_API_KEY` is set.)*

If she and the caterer need to work out details, she messages them directly from the booking — sending is unrestricted on her side regardless of whether that vendor is verified yet, and a small badge on her vendor list tells her at a glance which threads have something new waiting. If money's already changed hands on a booking, she can no longer remove that vendor or unlink them from a budget line until she marks the paid installment Refunded first — a real guard, not just a confirmation dialog. *(Routes: `/events/[id]/vendors/[eventVendorId]/chat`, `event_vendor_chat_reads`; `/events/[id]/vendors/[eventVendorId]`'s Remove Vendor control, guarded by `hasPaidInstallment()`.)* If something isn't working, or she just has a question, the FAQ and a "Report an Issue" form are both one tap away from her Profile tab — the report goes in as a real case she can track the status of afterward, not a dead-end contact form. *(Routes: `/faq`, `/profile/cases`, `/profile/cases/new`, `/profile/cases/[id]`.)*

## Part Two: The Vendor's Journey

He arrives already running a photography business, with two ways in. If Gather has never heard of his business, he registers fresh and becomes its Owner on the spot — no review needed, since there's no competing claim on a brand-new listing. *(Route: `/onboarding/vendor` — the self-registration-then-insert-self-as-Owner chicken-and-egg case, using a `SECURITY DEFINER` helper function to avoid the RLS recursion the naive version would hit.)*

If a planner already stubbed his business, he finds it, submits a claim with a short verification note, and waits for review. *(Route: `/vendors/[id]/claim`.)* An admin actually reviews it from a real queue — `/admin/vendors/claims`, part of the admin console's own build, not the placeholder the original draft of this doc described. When approved, he becomes Owner in one motion — the vendor flips to Verified, and any competing pending claim is automatically rejected in the same transaction. *(`approveClaim`/`rejectClaim`, `src/app/admin/vendors/claims/actions.ts`.)*

As Owner, he fills out the business profile, sets a real logo photo, lists what he offers, adds photos to a public gallery, and links his social accounts. *(Route: `/vendor/[vendorId]/dashboard`, `/vendor/[vendorId]/edit` — service listings, gallery, and social links all visible to anyone browsing `/vendors`, logged in or not.)* A "Complete your profile" card on his dashboard tells him plainly what's still missing and why it matters — a fuller profile ranks higher on Home and in the `/vendors` marketplace, right alongside (and below) any vendor with a live paid featured placement (an admin sets its dates, status, and whether it is pinned to a rank or rotates daily). When featured spots are open, he can ask for one himself as Owner — a "Get featured" card on his dashboard (or a "Your spot here" card at the end of the marketplace's Featured row) opens a short request: top spot or rotating, 1 week / 1 month / 3 months, a start date, and the listed price. It lands as Pending for an admin to confirm price and dates; nothing is charged in-app. *(Routes: `/vendor/[vendorId]/featured`, public prices at `/featured`; admins can switch the whole featured system off while the marketplace is small.)* *(`ProfileCompletionCard` + `getVendorCompletion()`, `src/lib/vendor-completion.ts` — the percentage itself is his alone to see; a planner browsing never sees a score, only the Featured/Verified badges it helps earn.)* He brings his second shooter on as a Manager and his assistant on as Staff — Managers can quote, manage bookings and see payments; Staff can chat with planners, add gallery photos, keep private team notes on a booking ("gate code 4411") and *suggest* a quote that a Manager sends or discards — but never see prices or payments, checked fresh on every request via `getVendorAccess(vendorId, userId)`, never cached in a session. *(Route: `/vendor/[vendorId]/team`, Owner-only.)* He can hold both identities at once — his own planner account and ownership of this business — so each time he logs in Gather asks "Who are you today?" and opens either Home or that business's dashboard; he can switch later from the persona switcher on his Profile tab. *(`/choose-persona`.)* When he opens a second studio, "+ Add a business" on his Profile takes him to the same setup form. He can own up to five businesses, one per category — a second photography business is refused, but the form lets him ask for an exception with a reason, and once an admin approves it he creates it as normal. *(`/onboarding/vendor`, `vendor_business_requests`, admin review at `/admin/vendors/requests`.)*

A planner associates his business with her event, and it shows up on his dashboard immediately — the live RLS join means he never has to be told, and a teammate added to his team *after* the booking already existed sees it too. He submits a quote; only Manager-tier and above can send one, so his Staff assistant can see the booking and suggest a figure, but the planner only sees it once he approves it — and the assistant never sees the business's other prices or payments. If it's accepted, he sees the payment plan and installments building up, with running totals computed by the database, not recalculated client-side.

He can message the planner from that same booking, but only once his listing is actually verified — until then he can still read anything sent to him, he just can't reply, which is what actually stops a freshly-created, unreviewed vendor stub from being able to message any planner it likes. A small badge on his dashboard's booking cards tells him which conversations have something new waiting, same as the planner's side. *(Route: `/vendor/[vendorId]/bookings/[eventVendorId]/chat`; the vendor-side branch of `event_vendor_messages`' INSERT policy gated on `is_vendor_verified`, planner side left unrestricted.)*

## Part Three: Cross-Cutting Flows

**Guest → authenticated transition.** A guest browsing `/` or `/vendors` who signs up mid-session lands back where they were with the tab set now reflecting their new persona — session state is a reactive Server Component read plus a Zustand store, not a one-shot publish requiring a deliberate reload.

**Persona switching.** A user with both a Planner identity and one-or-more Vendor personas switches via the switcher on their Profile tab — every vendor-scoped Server Action re-derives and re-checks access for the *specific* vendor being acted on via `getVendorAccess`, exactly as any other call would; the current persona is never trusted as a cached authorization decision.

**Getting help.** Two separate, deliberately lightweight paths exist rather than one combined one: the FAQ (`/faq`, public, no login needed — a guest deciding whether to sign up has as much reason to read it as an existing user) for "how does this work," and "Report an Issue" (`/profile/cases/new`, signed-in only) for "something's actually wrong with my account/booking/payment." A report becomes a real, trackable case — a category (grounded in the same four areas the FAQ itself is organized around: payments & billing, vendor booking & communication, event setup & guests, account & verification), free text, and an optional screenshot — visible afterward at `/profile/cases` with its current status, reaching the same admin case queue (`/admin/cases`) a phone-call-logged case would.

**Every drill-down page's header.** Not a feature a planner or vendor would describe as a "flow," but genuinely cross-cutting: every page reached by tapping into a list (as opposed to one of the bottom tab bar's own roots) shares one `PageHeader` component — a circular back button sitting beside the title, rather than the plain "‹ Back" text link stacked above it that shipped originally. Applies to every non-admin page in the app; `/admin/*` keeps its own separate desktop-oriented layout, deliberately not sharing this or any other piece of the mobile shell.

## Part Four: Journey → Test Plan Seed

Each beat above cites a route and, where the underlying mechanism matters, the action/policy/table making it real — deliberately, so a beat can be lifted close to directly into a concrete manual test case.

**Still not built, and still shouldn't be started from this doc alone:** a full `docs/gather_web_test_plan.md` with a real test-case table. Unlike when this doc was first written, that's no longer blocked on "the routes don't exist yet" — nearly everything above is real, clickable software today. It's still not written because `gather_web_architecture.md`'s own Verification section already carries a real, per-feature account of how each piece was actually verified (Playwright passes, RLS checks against live throwaway users, what was and wasn't confirmed) — extracting a separate test-plan doc now would either duplicate that record or, more likely, go stale exactly the way this doc itself just did once neither doc is the obviously-authoritative one. If a real QA test-plan doc becomes genuinely necessary (a second person joining who needs a checklist, not prose), the right source to build it from is the architecture doc's changelog, not this one — this doc's job is describing the shape of each journey, not enumerating its test steps.
