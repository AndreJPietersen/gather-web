# Gather Web — Epic Roadmap

**Status:** Living, working document — update directly as phases progress, same convention as the Salesforce-era `gather_frontend_epic_plan.md` this sequencing mirrors. Companion to `gather_web_architecture.md` (stack/data-model/RLS reference; the dated engineering log for completed phases lives there, not here) and `gather_web_user_journeys.md` (the narrative each phase is making real).

## Context

`gather_web_architecture.md` already ports the Salesforce ERD, RLS/authorization model, and a 10-phase sequence that mirrors the Salesforce-era 10-epic frontend plan almost 1:1. What that doc's Build Phases table didn't have — and what made the Salesforce-side `gather_frontend_epic_plan.md` genuinely useful during that build — was per-phase detail beyond one sentence, a concrete kickoff sequence for whatever's next, and a running Outstanding Items checklist tagged by the phase that surfaced each item. This doc adds all three, and is expected to be edited every session the way the Salesforce doc was.

Phases 0 through 9 — the entire originally-planned consumer-facing roadmap — are done, built and verified against a real local Supabase stack. See `gather_web_architecture.md`'s "Local environment setup log" for the full dated account. **Phase 10 (Admin & Support Console, see `gather_web_admin_architecture.md`) is the only phase left.** A handful of items remain genuinely open by necessity, not oversight — see Outstanding Items: two need Andre directly (a real mobile device test, a Stripe account), one needs a design decision (the OKLCH palette's measured contrast failures), and one is a deliberately deferred stack decision (background-job infrastructure for payment reminders).

## Phase 2 Kickoff Sequence (completed 2026-09-13)

Kept as a historical record of what was planned vs. what actually happened — see `gather_web_architecture.md`'s engineering log for the two real bugs found along the way (a cookie-mutating Server Action discarding its own return value, and why the persona store needed to be per-request rather than a global singleton).

1. Root layout (`src/app/layout.tsx` already exists from Phase 1 — extend it, don't replace it) gets a persistent bottom tab bar component, initially guest-only (Home / Vendors / Log In), matching the Screen/Route Inventory's tab sets.
2. A session-context source of truth: a small server-side helper (using `src/lib/supabase/server.ts`, already built in Phase 0) that reads the current Supabase Auth session and profile row, callable from both Server Components and Server Actions — the direct replacement for `SessionContextController.getSessionContext`, and deliberately **not** a one-shot context published only at shell-mount (that's the exact bug being fixed).
3. A Zustand persona-switcher store, seeded from the session helper's vendor-team memberships — no UI yet, just the store and its shape, so Phase 4/8 can build against a stable interface.
4. A minimal toast system (a Zustand store or React Context + a fixed-position renderer in the root layout) — no dependency on any feature work, safe to build in isolation and reuse everywhere.
5. Wire the tab bar to the session helper so it swaps between guest/planner/vendor tab sets live — this is the first real end-to-end proof that Phase 2's session plumbing works, the same role `PublicEventController.getPublicEvents` played as the "first real wire call" in the Salesforce kickoff sequence.
6. Verify in a real browser per the architecture doc's Verification section (not just `next build`) — sign in as a real local Supabase Auth user created via Phase 0's verification flow, confirm the tab set actually changes, confirm zero console errors, check the fixed bottom tab bar against iOS Safari's safe-area insets if a physical device or simulator is available.

Done exactly as planned, steps 1-5. Step 6 was verified with Playwright against a real dev server and a real local Supabase Auth user (guest → login → authenticated tab set → profile → logout → guest tab set again, zero console errors) — the one piece **not** yet checked is real iOS Safari safe-area-inset behavior, since that requires a physical device or simulator, neither available in this pass; carry that check forward to whenever a device is available, per the architecture doc's mobile-first testing requirement.

## Phase 4 Kickoff Sequence (completed 2026-09-13)

Done exactly as planned, all four steps — plus a real schema gap found and fixed along the way (`profiles` had no `phone` column, needed for planner onboarding) and two subtle Router-Cache/derived-state bugs that only surfaced testing the vendor path through the actual UI. ## Phase 6 Kickoff Sequence (completed 2026-09-13)

Kept as a historical record — see `gather_web_architecture.md`'s engineering log. Notably the first phase in a while with no new bug found; the work reused already-proven patterns closely enough (search-first flow, form shapes, a straightforward policy widening) that nothing new broke.

1. Add RLS policies for `vendor_services` and `vendor_claim_requests` (currently service-role-only) — services readable by anyone (they're part of a vendor's public profile), writable by Owner/Manager team members; claim requests visible to their claimant and to the vendor's existing team, insertable by any authenticated user.
2. Decide and resolve the dormant vendor-visibility gap flagged back in Phase 3: `vendors_select_public_or_own` only lets `anon` see `verification_status = 'verified'` vendors, but the documented bootstrapping workflow calls for unclaimed stubs to appear in the public directory too, marked Unverified. This phase is the one actually creating stubs, so the policy needs to change now, not stay dormant further.
3. Build `/vendors/add` — search-first (reusing `/vendors`' existing search), stub creation only after confirming no match, per the dedupe-before-create business rule.
4. Build `/vendors/[id]/claim` — a claim request form on the vendor profile page, shown when `verification_status !== 'verified'`, using the same `findUserByEmail`-style "resolve identity narrowly" pattern established in Phase 5 where relevant.
5. No admin approve/reject UI to decide on here anymore — resolved by adding Phase 10 (Admin & Support Console, see `gather_web_admin_architecture.md`), which owns that screen (`/admin/vendors/claims`). This phase only needs claims to actually exist and be submittable; reviewing them is Phase 10's job.

Done exactly as planned, all five steps — including updating `/vendors` itself to actually show unclaimed/claim_pending vendors (badged Unverified), not just widen the RLS policy without the directory page using it.

## Phase 7 Kickoff Sequence (completed 2026-09-13)

Kept as a historical record — see `gather_web_architecture.md`'s engineering log. One correction found while executing step 2/3 below: the one-Accepted-quote and installment-sum invariants were only ever *documented* intent in the Business Rules table, not actually built into the schema yet — this phase is the one that actually built both (a partial unique index and a trigger, respectively), not just added RLS on top of already-enforced invariants as originally assumed.

1. Add RLS policies for `vendor_quotes`, `payment_plans`, `payment_installments`, and `payment_reminders` (currently service-role-only) — scoped through `event_vendors` back to the event owner/editor-collaborator on the planner side, and through `vendor_team_members` (Manager+) on the vendor side, mirroring the two-sided access shape `event_vendors` itself already has.
2. Build `/events/[id]/vendors` — list `event_vendors` for the event, quote review, accept/decline. The one-Accepted-quote-at-a-time invariant (partial unique index, already in the schema) means the frontend just refreshes after either action rather than re-implementing that rule client-side.
3. Build `/events/[id]/payments` — payment plan creation, installments, marking paid. The installment-sum-≤-plan-total constraint is likewise already enforced at the DB level; don't duplicate a running-total check in the form.
4. Decide the Stripe integration's actual shape before wiring it in: at minimum, which side initiates a payment (planner marking an installment paid manually vs. a real checkout flow), and whether Phase 7 ships real Stripe test-mode charges or defers to a later hardening pass — `payment_installments` already reserves `payment_gateway`/`gateway_transaction_id`/`gateway_status` columns for this, so the schema isn't the blocker, the integration surface is.
5. There's no UI yet for a vendor to *submit* a quote in the first place (`VendorQuoteController.submitQuote`'s equivalent) — that's Phase 8's vendor dashboard, matching how the Salesforce build split planner-side commerce (Epic 7) from vendor-side quote submission (Epic 8). Phase 7 only needs to seed a quote via the service role or Studio for testing the planner-side accept/decline flow, not build the submission form itself.

Done, all five steps, plus one thing this plan didn't anticipate needing: there was no way to associate a vendor with an event at all until this phase added it to `/vendors/[id]` — without it, none of the pages built here would have been reachable through the product itself. Stripe was deliberately deferred per step 4's own framing — manual tracking is documented as the current intentional state (ERD Design Principle 9), and real integration needs Andre's own Stripe account, the same class of blocker as the still-pending Vercel login.

Full persona-switcher exercise: a user holding both a Planner identity and a Vendor persona for the vendor they're now managing — confirm switching between them via the Phase 2 persona switcher correctly changes which tab set and dashboard they see, the first time both personas' real screens exist simultaneously to switch between.

Done, all five steps — plus one thing step 2 flagged as "likely needs its own RLS policy set" turned out to need more than expected: `vendor_team_invites` is email-keyed, not `user_id`-keyed like every other invite table in this schema, which needed a genuinely new kind of helper function (reading `auth.users`, not just `public.*` tables). Step 4's live-join fix and step 5's persona switch were both proven together in one continuous test: a teammate invited before a booking existed, who then created that exact booking themselves (in their Planner persona) before ever accepting the vendor invite, then switched personas and saw it immediately.

Design and build a real notification-preferences schema — never existed at all, a genuine schema decision (which channels, per what event type, opt-in vs. opt-out defaults) rather than a quick add. ## Outstanding Items

A running checklist, tagged by the phase that surfaced or should close each item — kept separate from the Progress Log below so it stays scannable, same convention as the Salesforce-era doc. Nothing here blocks the current phase; each is either a deferred-by-design scope boundary or a real gap worth closing later.

- [x] **Guest home (`/`) doesn't branch on auth state.** Never done once in the Salesforce LWC build — fixed in Phase 3: an authenticated visitor sees a personalized welcome and quick links instead of the guest hero CTAs, both variants sharing the same live events/vendors content beneath. *(Phase 3.)*
- [x] **RSVP form needs real validation**, not a bare `if (!name || !email)` check — the Salesforce build shipped exactly that and flagged it as worth tightening later. Done properly in Phase 3: zod field-level validation server-side (name length, email format, guest-count bounds) plus native HTML5 validation client-side, both actually exercised and verified, not just written. *(Phase 3.)*
- [x] **URL should reflect the current tab/view.** Resolved by construction in Phase 2 — the tab bar links to real routes (`/`, `/vendors`, `/events`, `/profile`, `/vendor/[id]/dashboard`) and highlights active state from `usePathname()`, so the URL is always the source of truth for the current view, unlike LWR's unverified `NavigationMixin` behavior the Salesforce build never resolved. *(Phase 2.)*
- [x] **Vendor team "snapshot at association time" sharing bug — fix, don't repeat.** The Salesforce build documented this as "not fixable from the frontend": a teammate added to a vendor's team after a booking (`event_vendors` row) already existed wouldn't see it, because the sharing grant was snapshotted, not live. Not just confirmed by reading the policy — actually proven in Phase 8 with a real test: a teammate was invited, a booking was created for that vendor *before* they accepted, and the dashboard showed it to them immediately upon accepting. *(Phase 8 — proven, not just assumed.)*
- [x] **Money must render via `Intl.NumberFormat`, never string concatenation.** The Salesforce build rendered bare `R{amount}` everywhere commerce data appeared and never fixed it across 3 epics. Done in Phase 7: `formatZAR()` (`src/lib/utils.ts`) built once and used from the first commit that rendered any money at all. Confirmed reused correctly (not reinvented) in Phase 8's vendor dashboard, the second place money renders — the helper held up across both phases. *(Phase 7, confirmed in Phase 8.)*
- [x] **Admin claim approve/reject needs an actual screen.** Salesforce deferred this entirely to a Setup list view — gather-web has no equivalent free admin surface, so this was flagged as net-new work rather than a straight port. Resolved by scoping a full Phase 10 (Admin & Support Console, see `gather_web_admin_architecture.md`) rather than a one-off screen bolted onto Phase 6 or 9 — it ships as `/admin/vendors/claims`. *(Decided; ships in Phase 10.)*
- [x] **Notification/reminder preferences have no schema at all.** Never existed on the Salesforce side either (flagged there as "a schema decision, not a quick add"). Done in Phase 9: `notification_preferences` (one row per user, upserted on first save rather than seeded by a trigger), an email-reminders toggle wired into Profile, SMS/push left honestly disabled ("coming soon") rather than pretending those channels work. *(Phase 9.)* Actually *sending* reminders still needs background-job infrastructure (Edge Functions + `pg_cron`, or Inngest) — that decision remains genuinely open, tracked below.
- [~] **Vitest + React Testing Library coverage from the start.** The single biggest process gap the Salesforce frontend build called out in hindsight ("no LWC Jest tests were written across any of the ten epics") — the explicit intent this time was tests landing alongside each phase's components/Server Actions, not deferred to Phase 9 as a catch-up pass. **Honest assessment: that intent wasn't met** — no test infrastructure existed before Phase 9, meaning this repeated the exact anti-pattern it warned against for 8 phases. Phase 9 did set up real infrastructure (Vitest + RTL + jsdom, 16 passing tests) covering the shared UI primitives and pure utility functions — but async Server Components (every `page.tsx` in this project) aren't supported by Vitest at all per Next.js's own testing guide, so this is a smaller foundation than "full coverage," not a completed catch-up. Server Action business logic (zod schemas, RLS-dependent behavior) remains covered only by the manual Playwright pass each phase has gotten, not by this suite. *(Should have started Phase 2; actually started Phase 9.)*
- [x] **RLS policies for `event_attendees` and `event_tasks`** — done in Phase 5, owner-or-any-accepted-collaborator to read, owner-or-Editor to write, matching `events` itself. *(Phase 5.)*
- [x] **RLS policies for the remaining 7 tables** (`vendor_services`, `vendor_claim_requests`, `vendor_team_invites`, and the full commerce block) — all done: `vendor_services`/`vendor_claim_requests` in Phase 6, the full commerce block in Phase 7, `vendor_team_invites` in Phase 8. Every table in the schema now has real policies except `payment_reminders` (SELECT-only, deliberately — no UI writes these yet, see the background-jobs item below) and the new Phase 9 admin-adjacent tables (`support_cases`, `support_case_comments`, `admin_audit_log`, deliberately service-role-only per `gather_web_admin_architecture.md`). *(Phases 6–8.)*
- [x] **Unclaimed vendor stubs aren't visible to guests, contradicting the documented bootstrapping workflow.** `gather_erd_master.md` says unclaimed stubs should show in the public directory marked Unverified; the actual Phase 0 `vendors_select_public_or_own` RLS policy only lets `anon` see `verification_status = 'verified'` rows. Resolved in Phase 6: the policy now includes all three statuses, and the `/vendors` directory page itself was updated to actually query and badge all of them, not just verified ones. *(Phase 6.)*
- [ ] **Background-job infrastructure for `payment_reminders` is still undecided.** The stack table has named two candidates (Supabase Edge Functions + `pg_cron`, or Inngest) since Phase 0, but nothing has picked one — `payment_reminders` has a SELECT-only RLS policy and zero rows are ever created by anything. This is genuinely deferred, not forgotten: no phase's scope has needed it yet, but it can't stay open forever if payment reminders are meant to actually fire. *(Open since Phase 0; still open after Phase 9.)*
- [ ] **OKLCH brand palette has real, measured WCAG AA contrast failures.** Computed properly in Phase 9 (OKLCH → linear sRGB → WCAG relative luminance, not eyeballed): `primary` text on `bg` (3.87:1, needs 4.5), white button text on `primary` (4.36:1), `primary` text on `primary-soft` badges (3.28:1), and `success` green text on `bg` (2.07:1, a serious failure even for large text) all fail. None of this project's actual UI text is large enough (≥18.66px bold or ≥24px) to use the looser 3:1 threshold, so 4.5:1 is the real bar everywhere. **Deliberately not fixed**: these are the confirmed, stakeholder-approved brand colors from the ported prototype, and adjusting them is a design decision, not a technical one — flagging for a human call rather than unilaterally darkening the brand magenta. *(Found in Phase 9, needs a design decision.)*
- [ ] **No real physical mobile device has ever tested this product.** Every phase's "mobile-first" verification has been Playwright/Chromium — real device presets (correct viewport, touch, pixel ratio) were added in Phase 9 and caught nothing new, but Chromium fundamentally cannot validate `env(safe-area-inset-*)` behavior the way WebKit/real iOS Safari does, a gap the architecture doc's own Verification section has named since Phase 2. This needs Andre's own phone, the same category of blocker as the still-pending Vercel login and Stripe account. *(Open since Phase 2; still open after Phase 9.)*
